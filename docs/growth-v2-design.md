# IdleRaid 성장 통합 v2 설계

기준: 프로젝트의 IdleRaid_Codex_Integration_v2.md와 현재 Luau 구현. 아래 수치는 이 게임을 위한 테스트 가정이다. 경쟁작의 공식이나 실측 수치가 아니다.

## 데이터와 지급 경로

| 값 | 의미 | 변경 규칙 |
| --- | --- | --- |
| AvailableTrainingPower | 현재 돌파에 사용할 수련력 | 지급 시 증가, 돌파 비용만 차감 |
| LifetimeTrainingPower | 전체 누적 수련력 | 지급 시 증가, 소비해도 감소하지 않음 |
| Level, Exp | 누적 수련력에서 계산한 표시와 전투 성장 | 별도 EXP 장부 없음 |
| BreakthroughStage | 지속 수련 배수 단계, 1~30 | 무료 +1 또는 보유권 +2/+3/+5 |
| TrainingFacilityTier | Gold로 구매한 시설, 1~4 | 시설 배수는 교체 적용 |
| ClearedRaidGates | 10/20/30단계 관문 최초 클리어 | 실제 RaidRun 성공 및 유효 공격 필요 |

AddPowerFinal은 이미 계산된 최종 수련력만 한 번 더한다. 온라인 수련은 서버 경과 시간으로, 적 처치는 서버가 확정한 Enemy/구간으로, 레이드는 서버가 확정한 성공으로 지급한다. 클라이언트의 보상량이나 자칭 수동 전투 플래그를 받지 않는다.

## 성장 공식

현재 단계 s의 배수는 2^(s-1)이다. 기준 수련속도는 10 × 2^(s-1)/초, 실제 기본 수련속도는 기준 속도에 현재 시설 배수를 한 번 적용한 값이다. 시설 배수는 1.0, 1.5, 2.0, 3.0이다. 돌파 시간 목표는 min(900, 45 + 15 × (s-1))초다. 돌파 비용은 기준 속도 × 시간 목표이며 시설 등급이나 상품 보유 여부가 비용을 올리지 않는다.

| 단계 | 배수 | 기준 수련력/초 | 다음 단계 비용 |
| ---: | ---: | ---: | ---: |
| 1 | 1 | 10 | 450 |
| 9 | 256 | 2,560 | 422,400 |
| 10 | 512 | 5,120 | 921,600 |
| 19 | 262,144 | 2,621,440 | 825,753,600 |
| 20 | 524,288 | 5,242,880 | 1,730,150,400 |
| 29 | 268,435,456 | 2,684,354,560 | 1,248,224,870,400 |
| 30 | 536,870,912 | 5,368,709,120 | 콘텐츠 상한 |

레벨 1의 다음 요구량은 100이다. 이후 요구량을 정수로 약 1.3배 늘린 누적 임계값에서 이진 검색으로 Level과 Exp 진행도를 구한다. 최대 레벨은 100이다. Attack은 기존 기본값, 레벨 보너스, 장비 보너스를 더한다. 수련 배수를 Attack에 곱하지 않는다.

수련력은 0~9,007,199,254,740,991의 정확한 정수 범위에 제한한다. 상한 밖 지급이나 연산은 거부한다. 초당 속도의 1/1000초 나머지는 온라인 정산 커서에 남긴다. 화면은 K/M/B/T/Qa로 축약하지만 서버 판단에는 원본 정수만 사용한다.

## 무료 경로, 권, 관문

무료 +1은 현재 단계 비용 1회분만 지불한다. +2/+3/+5권도 같은 현재 단계 비용 1회분과 권 1장을 사용하고 해당 단계 수만큼 이동한다. 건너뛴 단계의 비용을 합산하지 않는다. 권은 구매나 토큰 교환으로 먼저 소유하고, 조건이 맞을 때 사용한다.

첫 미클리어 관문 단계(10, 20, 30)에 도달하는 것은 허용한다. 그 단계를 넘어가는 요청은 거부하며 지갑과 권을 건드리지 않는다. 부분 적용은 없다. 30단계 관문 클리어가 이번 프로토타입의 최종 목표다.

Slime King은 기존 RaidService/EnemyService를 공유하며 Gate10/20/30에서 HP와 Gold/Token 보상만 설정별로 달라진다. 보스 피해 판정과 참가/공격 기록은 서버가 담당한다. 관문 기록은 입장 시 해당 단계와 선행 관문 자격이 있었고, 팀이 실제로 승리했으며, 본인이 유효한 피해를 한 참가자에게만 준다. 일반 레이드 보상은 팀 참가자에게 지급한다. 실패해도 영구 단계는 감소하지 않는다.

RaidToken으로 같은 +2/+3/+5권을 각각 10/18/30토큰에 교환한다. Gate10은 1토큰, Gate20은 3토큰, Gate30은 6토큰을 지급하는 테스트 설정이다. 다른 토큰 수입이 없고 Gate10만 반복하면 +2권에는 최소 10회, +3권에는 18회, +5권에는 30회 클리어가 필요하다. 이 횟수는 전투 소요와 대기시간을 제외한 최소치다.

## 수련 시간권과 상품

10/30/120분권은 사용 시점의 기본 수련속도에 각각 600/1800/7200초를 곱해 즉시 수련력을 준다. 기본 속도 120/초의 10분권은 정확히 72,000이다. 이 지급량에 단계·시설 배수를 다시 곱하지 않는다. 미리보기 이후 속도나 보유량이 바뀌면 사용 요청을 거부하고 새 미리보기를 요구한다.

고정 상품 계약은 +2/+3/+5권과 10/30/120분권 각각 1장이다. MonetizationEnabled=false이며 모든 ProductId와 가격은 미설정이다. 현재 UI는 구매를 “준비 중”으로 표시하고 실제 결제 요청을 보내지 않는다. Studio 전용 개발 패널의 모의 지급과 모의 영수증은 Robux 지출 없이 계약을 시험한다. 판매 연결 시 가격은 플레이어에게 적용되는 Roblox 상품 정보에서 조회해야 하며 추정 가격을 적지 않는다.

## 프로필과 오프라인

IdleRaid_Profile_v2 한 레코드가 수련력, Gold, RaidToken, Inventory, Equipment, 권, 관문, 처리한 PurchaseId, 정산 시각을 보관한다. DataStore는 운영 서버에서만 사용하고 Studio는 메모리 모의 저장소를 사용한다. UpdateAsync 콜백은 원본을 변환해 반환하며 외부 지급이나 Remote 전송을 수행하지 않는다. 세션 소유자와 만료 시각으로 동시 서버 저장을 막고, 자동 저장·퇴장·종료 시 저장한다. 잠금 상실이나 로드 실패 시 프로필을 Ready로 제공하지 않는다.

이전 Level/Exp는 기존 레벨 안의 진행 비율을 새 누적 임계값으로 한 번 옮긴다. 이전 Gold, RaidToken, 유효한 장비·인벤토리·소유권은 보존한다. 구버전에 없던 사용 가능 수련력은 0, 단계는 1로 시작한다. 변환된 누적량을 소비 지갑에 중복 지급하지 않고, 과거 일반 보스 처치로 관문 기록을 만들지 않는다. 지원하지 않는 미래 버전과 손상 데이터는 로드 거부한다.

오프라인 수련력은 저장된 기준 수련속도 × 인정 경과 시간(최대 8시간) × 25%다. 저장된 시점의 속도를 사용하고, 새 단계·시설 효과를 과거 시간에 소급하지 않는다. 정산 지급과 시각 커서는 같은 프로필 변경으로 저장한다. 오프라인 Gold, 장비, 토큰, 자동 돌파는 없다.

실제 게시 Experience의 DataStore 권한과 두 서버 경쟁은 이번 Studio 모의 테스트와 다르다. 운영 자료의 재설정·수정은 수행하지 않는다. 영수증은 PurchaseId와 계약 버전을 함께 영구 보관하고, 같은 프로필 저장 성공 전에는 PurchaseGranted를 반환하지 않는다. 실패 시 같은 영수증을 재시도하며 중복 지급하지 않는다.

## 시뮬레이션 해석과 출처

tests/growth-v2-simulate.luau가 실제 GrowthConfig, GrowthMath, GameConfig를 require해 docs/growth-v2-economy.csv를 생성한다. 자동사냥 8킬/분, 직접 플레이 10킬/분, 관문 전투 60/90/120초는 측정값이 아닌 비교 가정이다. 두 사냥 경로는 같은 시설 구매 정책을 따른다. 실제 기기와 플레이어 행동의 속도는 별도로 측정해야 한다. 전투 시간을 제외한 성장 시간과 관문 전투 시간을 CSV에서 분리한다.

Roblox API 확인 자료: [Developer products](https://create.roblox.com/docs/production/monetization/developer-products), [Data stores](https://create.roblox.com/docs/cloud-services/data-stores), [Player data and purchases](https://create.roblox.com/docs/cloud-services/data-stores/player-data-purchasing). 이 링크는 Roblox API 계약의 근거이며 위 성장 계수의 근거가 아니다.

## 판매 연결 전 체크리스트

이번 커밋에서는 판매가 비활성이고 ProductId·가격이 모두 nil이다. 다음 작업에서 실제 판매를 연결하려면 각 6개 고정 계약에 대해 Experience 소유권이 맞는 Developer Product를 만들고 ProductId 중복 여부를 확인해야 한다. 가격 표시는 플레이어에게 적용되는 Roblox 상품 정보로 조회하며 숫자를 코드에 추정해 적지 않는다. 게시된 별도 테스트 Experience에서 ProcessReceipt의 중복 호출, 저장 실패 후 재호출, 재접속, 두 서버 경쟁, 상품 미설정·폐기 상황을 검증해야 한다. 현재 Studio 모의 영수증 성공을 실제 Robux 결제 성공으로 간주하지 않는다.

운영 DataStore로 전환할 때는 이전 프로필의 1회 마이그레이션과 백업, 세션 잠금 만료 정책, UpdateAsync 예산과 오류 재시도, 서버 종료 시 저장 시간, 프로필 크기 및 구매 장부 증가를 확인해야 한다. 개발용 지급 Remote는 Studio에서만 생성되며 게시 서버에는 존재하지 않아야 한다.
